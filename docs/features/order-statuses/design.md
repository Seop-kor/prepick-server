# 주문 목록 상태 필터

## Problem Statement

주문 목록을 사용하는 클라이언트는 진행 중인 주문만 화면에 보여 주고 싶지만, 기존 `orders` 쿼리는 사용자의 모든 주문을 반환한다. 클라이언트가 여러 페이지를 모두 가져온 뒤 직접 필터링하면 불필요한 데이터를 주고받고, 필터링 전 개수를 기준으로 페이지네이션하면 페이지마다 표시되는 주문 수가 달라진다.

## Solution

기존 `orders` 쿼리에 선택적인 `statuses` 인자를 추가한다. 클라이언트는 필요한 `OrderStatus` 값들을 전달하고, 서버는 그중 하나라도 일치하는 본인 주문만 기존과 같은 최신순 페이지로 반환한다. 진행 중인 주문 화면은 예를 들어 `CREATED`, `CONFIRMED`, `IN_PROGRESS`, `READY`를 전달해 원하는 목록을 얻는다.

상태 필터를 생략한 기존 요청은 그대로 동작한다. 필터가 적용된 페이지의 커서는 같은 상태 조합에서만 사용할 수 있게 해 필터를 바꾼 뒤에도 이전 페이지 경계가 잘못 적용되는 것을 막는다.

## User Stories

1. 주문 화면을 개발하는 클라이언트 개발자로서, 진행 중으로 표시할 상태들을 `statuses`로 전달하고 싶다. 그래야 진행 중인 주문만 화면에 표시할 수 있다.
2. 클라이언트 개발자로서, 여러 상태를 한 번에 전달하고 OR 조건으로 조회하고 싶다. 그래야 상태별로 쿼리를 여러 번 실행하지 않을 수 있다.
3. 클라이언트 개발자로서, `PICKED_UP`과 `CANCELED`도 같은 필터로 조회하고 싶다. 그래야 주문 이력과 취소 주문 화면에서도 같은 API를 재사용할 수 있다.
4. 기존 API 사용자로서, `statuses` 인자를 생략한 요청이 지금과 같은 전체 주문 목록을 반환하길 원한다. 그래야 클라이언트를 즉시 수정하지 않아도 된다.
5. 클라이언트 개발자로서, `statuses`를 null 또는 빈 배열로 볼 때도 필터를 생략한 것과 같은 결과를 받고 싶다. 그래야 선택적 변수를 구성할 때 특별한 분기를 두지 않아도 된다.
6. 클라이언트 개발자로서, 필터링된 결과 안에서 기존 커서 페이지네이션을 사용하고 싶다. 그래야 모든 주문을 한 번에 가져오지 않고도 진행 중인 주문의 다음 페이지를 볼 수 있다.
7. 클라이언트 개발자로서, 필터된 목록도 기존처럼 생성 시각과 ID 기준 최신순으로 정렬되길 원한다. 그래야 필터 도입 전후의 화면 순서가 일관된다.
8. 클라이언트 개발자로서, 같은 상태 조합의 순서나 중복 표현이 달라도 같은 페이지네이션을 이어 가고 싶다. 그래야 상태 목록을 정렬하거나 중복 제거하기 위한 불필요한 클라이언트 로직을 만들지 않아도 된다.
9. API 사용자로서, 다른 상태 조합에서 발급된 커서를 사용하면 명확한 입력 오류를 받고 싶다. 그래야 의도하지 않은 경계에서 잘린 목록을 정상 응답으로 오인하지 않는다.
10. API 사용자로서, 필터에 없는 잘못된 상태 값을 볼 때 GraphQL 검증 오류를 받고 싶다. 그래야 잘못된 요청을 빠르게 고칠 수 있다.
11. 서버 개발자로서, 상태 필터가 다른 사용자의 주문 접근 범위를 넓히지 않길 원한다. 그래야 기존 소유권 경계를 유지할 수 있다.
12. 테스트 실행자로서, 준비된 테스트 사용자와 주문 fixture를 이용해 Hurl로 실제 GraphQL API의 상태 필터를 검증하고 싶다. 그래야 HTTP 요청부터 데이터베이스 조회 결과까지 함께 확인할 수 있다.

## Implementation Decisions

- `orders` 쿼리에 nullable한 `statuses: [OrderStatus!]` 인자를 추가한다. 목록의 각 원소는 null일 수 없으며, 인자 자체는 생략하거나 null로 전달할 수 있다.
- `OrderStatus`의 모든 값을 필터로 허용한다. 서버가 '진행 중' 상태 조합을 새로 정의하거나 고정하지 않고, 클라이언트가 전달한 상태 집합을 그대로 사용한다.
- 상태가 하나 이상 지정되면 `status IN (...)`에 해당하는 OR 필터를 적용한다. 상태 값은 SQL 파라미터로 전달한다.
- `statuses`의 생략, null, 빈 배열은 모두 필터 없음으로 처리한다. 이 경우 기존 주문 목록 쿼리와 같은 조건과 커서 scope를 사용한다.
- 필터가 있을 때는 상태 목록에서 중복을 제거하고 정렬한 값을 사용한다. SQL 필터와 커서 scope가 같은 정규화된 상태 집합을 공유하므로 상태 순서와 중복은 결과와 커서 호환성에 영향을 주지 않는다.
- 커서 scope에는 사용자 ID와 정규화된 상태 집합을 함께 반영한다. 필터가 없는 경우에는 기존 사용자 ID scope를 유지해 이미 발급된 필터 없는 커서의 호환성을 보존한다.
- 다른 상태 집합으로 발급된 커서를 사용하거나 필터 있는 커서를 필터 없는 요청에 사용하면 기존 커서 검증 경로를 통해 `BAD_USER_INPUT`을 반환한다.
- 기존 `(created_at, id)` 내림차순 정렬, 커서의 생성 시각·ID 경계, `size` 검증, `size + 1` 조회 방식, `OrderPage` 응답 구조는 변경하지 않는다.
- 주문 소유권 조건인 `user_id`는 상태 필터와 무관하게 항상 적용한다. 주문 항목을 한 번에 조회하는 기존 방식도 유지한다.
- 서비스의 `findOrders`는 기존 인자 뒤에 선택적인 `statuses`를 받고, resolver는 GraphQL 인자를 그대로 전달한다. 새 입력 DTO나 공통 페이지네이션 추상화는 추가하지 않는다.
- GraphQL enum 검증에 맡기므로 정의되지 않은 상태 문자열에 대한 서비스의 별도 검증 분기는 추가하지 않는다.

## Acceptance Criteria

- [ ] AC-1: `orders` 쿼리는 선택적 `statuses: [OrderStatus!]` 인자를 GraphQL 스키마에 노출한다.
- [ ] AC-2: `statuses`에 하나 이상의 상태를 전달하면 그중 하나라도 일치하는 본인 주문만 반환한다.
- [ ] AC-3: 진행 중 상태뿐 아니라 `PICKED_UP`, `CANCELED`를 포함한 모든 `OrderStatus` 값을 필터에 사용할 수 있다.
- [ ] AC-4: `statuses` 생략, null, 빈 배열은 모두 상태 필터를 적용하지 않은 기존 목록과 같은 결과를 반환한다.
- [ ] AC-5: 필터 유무와 관계없이 결과는 생성 시각과 ID 기준 최신순이며 기존 `OrderPage` 구조와 `size` 규칙을 유지한다.
- [ ] AC-6: 필터된 첫 페이지의 `nextCursor`를 같은 상태 집합의 다음 요청에 사용하면 필터된 나머지 주문을 중복 없이 이어서 반환한다.
- [ ] AC-7: 같은 상태 집합의 순서를 바꾸거나 상태를 중복해서 넣어도 같은 필터의 커서를 사용할 수 있다.
- [ ] AC-8: 다른 상태 집합의 커서를 사용하거나 필터 있는 커서를 필터 없는 요청에 사용하면 `BAD_USER_INPUT` 오류를 반환한다.
- [ ] AC-9: 기존 필터 없는 목록에서 발급한 커서는 계속 필터 없는 다음 페이지 요청에 사용할 수 있다.
- [ ] AC-10: 정의되지 않은 상태 값을 전달하면 주문 조회를 실행하지 않고 GraphQL 입력 검증 오류를 반환한다.
- [ ] AC-11: 상태 필터를 사용하는 경우에도 다른 사용자의 주문은 결과에 포함되지 않는다.
- [ ] AC-12: 준비된 인증 변수와 주문 fixture를 사용한 Hurl E2E가 필터링, 빈 필터, 페이지네이션, 커서 불일치 동작을 실제 GraphQL HTTP 응답으로 검증한다.

## Testing Decisions

- 외부에서 관찰 가능한 GraphQL 응답과 오류를 검증하며, SQL 문자열이나 private 메서드 호출 횟수를 새로운 행동 테스트의 기준으로 삼지 않는다.
- 핵심 검증 경계는 Hurl GraphQL E2E다. 실행 중인 서버에 실제 HTTP 요청을 전송하고 응답의 주문 ID·상태·정렬·nextCursor·오류 코드를 확인한다.
- Hurl 실행에는 `base`와 유효한 `accessToken`을 외부 변수로 전달한다. 토큰은 다른 데이터와 섞이지 않는 전용 테스트 사용자의 것이어야 한다.
- 전용 테스트 사용자에게 상태와 생성 시각이 알려진 주문 fixture를 미리 준비한다. 진행 중 상태 여러 건과 완료·취소 상태를 포함하고, 필터된 다음 페이지를 확인할 수 있을 만큼의 주문이 필요하다. 다른 사용자의 주문도 소유권 확인용으로 준비한다.
- Hurl 시나리오는 상태 OR 필터, 완료·취소 상태 필터, 생략·null·빈 배열, 같은 필터의 다음 페이지, 상태 순서·중복 정규화, 필터 없는 커서 호환성, 다른 필터의 커서 거부, 잘못된 enum 값을 다룬다.
- 기존 GraphQL 스키마 테스트는 `statuses` 인자의 타입과 null 허용 여부를 확인하도록 갱신한다. 기존 resolver 테스트는 새 인자가 서비스에 전달되는지 확인하도록 갱신한다.
- Hurl 실행 전 fixture를 만들거나 삭제하는 자동 스크립트는 추가하지 않는다. 기존 smoke 테스트와 마찬가지로 실행 환경과 필요한 데이터를 외부에서 준비한다.
- 기존 주문 서비스·스키마·resolver 테스트는 회귀 확인을 위해 유지한다. 이번 설계에서는 새로운 Jest 실DB 통합 테스트 경계를 추가하지 않는다.

## Out of Scope

- 서버가 정의하는 '진행 중' 상태 상수, 기본 상태 목록, 별도의 `inProgress` 인자
- 주문 상태 전이나 주문 생성·상세 API의 변경
- 데이터베이스 스키마, 인덱스, 마이그레이션 변경
- 주문 목록의 정렬 기준, 페이지 크기 제한, 응답 필드 변경
- 공통 커서 인코딩 형식이나 다른 도메인의 커서 scope 변경
- Hurl용 사용자 생성, 로그인, 토큰 발급, DB fixture setup·cleanup 자동화
- 클라이언트 애플리케이션의 진행 중 주문 화면 구현

## Further Notes

- Hurl fixture는 반복 실행 시 같은 결과를 내야 한다. 전용 사용자의 주문 수, 상태 분포, 생성 시각이 알려져 있어야 하며 테스트 중 해당 데이터를 변경하지 않는다.
- access token은 만료되지 않은 값을 실행 시점에 제공한다. 토큰과 실제 데이터 준비는 실행 환경의 책임이며 저장소에 비밀 값을 기록하지 않는다.
- 클라이언트가 진행 중인 주문을 조회할 때 사용할 상태 조합은 서버 스키마나 공통 상수로 고정하지 않는다. 화면 요구사항이 바뀌면 서버 배포 없이 전달하는 `statuses`를 조정할 수 있다.
- 커서는 기존과 같이 opaque 값이다. 클라이언트는 커서 payload의 scope를 만들거나 해석하지 않고 응답의 `nextCursor`를 그대로 다음 요청에 전달한다.
