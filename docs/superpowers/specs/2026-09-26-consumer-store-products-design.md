# Consumer 매장 상품(메뉴) GraphQL 설계

## 목표와 범위

로그인한 Consumer App 사용자가 매장 상세 화면에서 카테고리 탭과 상품 목록을 보고, 상품 상세에서 주문할 하위 상품(SKU)과 품절 여부를 확인한다. PRD 8.3의 REST 경로는 기능 목록으로 해석하고, 서비스 용어에 맞춰 menu 대신 product를 사용한다.

| PRD 8.3 | 대응 기능 | GraphQL |
|---|---|---|
| `GET /stores/:storeId/menus` | `GET /stores/:storeId/products` | `storeProducts(storeId)` |
| `GET /menus/:menuId` | `GET /products/:productId` | `product(id)` |

이번 범위는 조회 전용이다. 옵션(Modifier), 다국어 이름, 뱃지, 재고 수량, 관리자 API는 추가하지 않는다. "인기"는 일반 카테고리 하나로 다룬다.

카테고리·상품 관계와 응답 모양은 이전 서비스의 GraphQL 스키마(`Category`, `ProductCategory`, `StoreProducts`, `SkuLocation.available`)를 참고했다.

## 데이터 스키마 (PostgreSQL)

기존 `product`, `sku` 테이블에 컬럼을 추가하고 카테고리 테이블 두 개를 만든다.

```sql
ALTER TABLE product ADD COLUMN description text, ADD COLUMN image_url text;
ALTER TABLE sku ADD COLUMN is_sold_out boolean NOT NULL DEFAULT false;

CREATE TABLE category (
  id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  store_id integer NOT NULL,
  name varchar(50) NOT NULL,
  sort_order integer NOT NULL DEFAULT 0,
  is_active boolean NOT NULL DEFAULT true
);

CREATE TABLE product_category (
  category_id integer NOT NULL,
  product_id integer NOT NULL,
  sort_order integer NOT NULL DEFAULT 0,
  PRIMARY KEY (category_id, product_id)
);

CREATE INDEX category_store_id_idx ON category (store_id) WHERE is_active;
```

- 상품과 카테고리는 다대다다. 한 상품이 "인기"와 "커피"에 동시에 속할 수 있다.
- `category.sort_order`는 매장 안의 탭 순서, `product_category.sort_order`는 카테고리 안의 상품 순서다.
- `product_category`는 별도 ID 없이 복합 PK를 쓴다. 매장 ID는 `category`와 `product`에서 얻을 수 있으므로 두지 않는다.
- `sku.is_active`는 게시 여부, `sku.is_sold_out`은 일시 품절이다. 품절은 SKU 단위로 관리하므로 "HOT 품절, ICE 판매"를 표현할 수 있다.
- 기존 방침대로 외래 키는 추가하지 않는다. DDL과 샘플 데이터는 사용자가 직접 실행하며 저장소에 SQL·seed 파일을 추가하지 않는다. 샘플 데이터 삽입 SQL은 구현 결과에 제공한다.

## GraphQL 계약

모든 쿼리는 기존 전역 인증 guard를 통과해야 한다.

```graphql
type Query {
  storeProducts(storeId: ID!): StoreProducts
  product(id: ID!): Product
}

type StoreProducts {
  categories: [Category!]!
  products: [Product!]!
}

type Category {
  id: ID!
  name: String!
  productIds: [ID!]!
}

type Product {
  id: ID!
  storeId: ID!
  name: String!
  description: String
  imageUrl: String
  minPrice: Int!
  isSoldOut: Boolean!
  skus: [Sku!]!
}

type Sku {
  id: ID!
  name: String!
  price: Int!
  isSoldOut: Boolean!
}
```

`StoreProducts`는 상품을 `products`에 한 번만 담고, 카테고리는 `productIds`로 상품을 참조한다. 여러 카테고리에 속한 상품의 중복 전송을 막기 위한 구조이며, 클라이언트는 `products`를 ID로 색인한 뒤 탭별 목록을 만든다.

```ts
const byId = new Map(products.map((p) => [p.id, p]));
const tabProducts = category.productIds.map((id) => byId.get(id)!);
```

목록과 상세는 같은 `Product` 타입을 사용한다. `storeId`는 장바구니의 "한 매장 상품만" 검사에 쓴다. 매장 객체가 필요하면 기존 `store(id)`를 조회한다.

## 조회 규칙

노출 조건은 기존 `search.menus`와 맞춘다. 상품은 소속 매장, 상품, 하나 이상의 SKU가 모두 활성일 때만 노출한다. 비활성 SKU는 응답에 포함하지 않는다.

- `storeProducts(storeId)`: 매장이 없거나 비활성이면 `null`을 반환한다.
  - `products`: 노출 조건을 만족하는 매장 상품을 이름 오름차순, ID 오름차순으로 반환한다. 카테고리에 속하지 않은 상품도 포함한다.
  - `categories`: 활성 카테고리를 `sort_order` 오름차순, ID 오름차순으로 반환한다.
  - `productIds`: `product_category.sort_order` 오름차순, 상품 ID 오름차순이다. `products`에 포함된 상품만 남긴다. 비활성 상품, 활성 SKU가 없는 상품, 다른 매장 상품에 연결된 행은 제외된다.
  - 남은 `productIds`가 비어 있는 카테고리는 반환하지 않는다.
- `product(id)`: 노출 조건을 만족하는 상품 한 건을 반환한다. 아니면 `null`이다.
- `skus`: 활성 SKU를 가격 오름차순, ID 오름차순으로 반환한다.
- `minPrice`: 활성 SKU 가격의 최솟값이다. 품절 SKU도 포함한다.
- `Product.isSoldOut`: 활성 SKU가 모두 품절이면 `true`다. 품절 상품도 숨기지 않고 표시하며, 선택 제한은 클라이언트가 처리한다.

매장 메뉴는 규모가 작다고 보고 페이지 없이 한 번에 반환한다. `storeId`와 `id`는 양의 32비트 정수 문자열이어야 하며, 잘못된 값은 GraphQL 입력 오류로 반환한다.

## 모듈 구조

상품이 전용 쿼리와 카테고리를 갖게 되므로 `src/products/` 모듈로 분리한다. 기능 추가 전에 동작 변경 없는 리팩터를 먼저 커밋한다.

### 1단계: 리팩터

| 현재 | 변경 |
|---|---|
| `src/stores/discovery.pagination.ts` | `src/stores/stores.util.ts` (`validateId` 제외) |
| `src/stores/discovery.types.ts` | `src/stores/stores.types.ts` |
| `discovery.pagination.ts`의 `validateId` | `src/common/validation.ts` |
| `src/stores/product.*`, `sku.*` | `src/products/` |
| `test/stores/discovery.pagination.spec.ts` | `test/stores/stores.util.spec.ts`, `validateId` 테스트는 `test/common/validation.spec.ts` |
| `test/stores/discovery.graphql.spec.ts` | `test/stores/stores.graphql.spec.ts` |

- `discovery`는 8.2 기능 이름(홈·매장 탐색)이라 파일 역할을 드러내지 못하므로 모듈 접두어 이름으로 바꾼다.
- `validateId`는 DI가 필요 없는 순수 함수이므로 `UtilService`가 아닌 함수 파일에 둔다.
- `StoresModule`의 `forFeature`에는 `StoreSchema`만 남긴다. `search.menus`는 raw SQL로 `product`, `sku`를 조회하므로 `StoresModule`에 그대로 둔다.
- 기존 spec·plan 문서의 `discovery` 표기는 과거 기록이므로 수정하지 않는다.

### 2단계: 기능

```text
src/products/
  product.entity.ts, product.schema.ts   description, imageUrl 추가
  sku.entity.ts, sku.schema.ts           isSoldOut 추가
  products.types.ts                      StoreProducts, Category, Product, Sku GraphQL 타입
  products.service.ts
  products.resolver.ts
  products.module.ts                     forFeature([ProductSchema, SkuSchema])
```

- `AppModule`에 `ProductsModule`을 등록한다.
- 조회는 기존 서비스처럼 `em.execute` raw SQL을 사용한다. `category`, `product_category`에는 엔티티를 만들지 않는다.
- `storeProducts`는 세 번 조회한다. 활성 매장 확인, 상품·활성 SKU JOIN 조회, 카테고리·`product_category` 조회 순서다. 상품별 SKU 묶음과 `minPrice`, `isSoldOut` 계산, `productIds` 필터링은 서비스에서 처리한다. 상품 수와 관계없이 조회 횟수가 고정되므로 N+1이 없다.
- `product`는 상품·매장·활성 SKU를 한 번에 조회한다.

## 검증

단위 테스트는 `em`을 mock하며 DB 테이블 없이 실행할 수 있어야 한다. 테스트 이름은 `~하면 ~한다` 형식으로 쓴다.

- 리팩터 후 기존 테스트가 모두 통과한다.
- 카테고리·상품·SKU 정렬.
- SKU 일부 품절과 전체 품절의 `isSoldOut`, 품절 SKU를 포함한 `minPrice`.
- 비활성 매장·상품·SKU·카테고리, 활성 SKU가 없는 상품, 다른 매장 상품 연결 제외.
- 빈 카테고리 제외, 카테고리 없는 상품 포함.
- 잘못된 `storeId`·`id` 입력 오류, 없는 대상의 `null` 반환.
- GraphQL 스키마 노출과 `schema.gql` 재생성.

실제 DB 연동 검증은 사용자가 DDL과 샘플 데이터를 적용한 뒤 수행한다.
