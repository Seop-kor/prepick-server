# Consumer 주문 GraphQL 설계

## 목표와 범위

로그인한 Consumer App 사용자가 결제를 마친 장바구니를 주문으로 기록하고, 자신의 주문 목록과 주문 상세를 조회한다. PRD 8.4의 REST 경로는 기능 목록으로 해석하고 GraphQL로 제공한다.

| PRD 8.4 | GraphQL |
|---|---|
| `POST /orders` | `createOrder(input)` |
| `GET /orders` | `orders(size, cursor)` |
| `GET /orders/:orderId` | `order(id)` |

### 전제: 결제 후 기록

`createOrder`는 결제(현금·카드 등)가 끝난 뒤 호출된다. 따라서 이 API는 주문을 **검증하는** 곳이 아니라 이미 확정된 거래를 **기록하는** 곳이다.

- 금액, 상품명, SKU명, 단가는 클라이언트가 보낸 결제 시점 스냅샷을 그대로 저장한다. 서버는 DB 가격과 비교하지 않고, `amount`와 항목 합계(`Σ price × quantity`)의 일치도 검사하지 않는다.
- 품절, 매장 영업 여부, 상품·SKU 활성 여부, 단일 매장 여부는 검사하지 않는다. 결제 후 거절하면 결제된 돈에 대응하는 주문이 남지 않기 때문이다. 이 검증은 결제 전 단계(클라이언트, 이후 결제 연동)의 책임이다.
- 실제 결제 연동을 추가할 때는 결제 단계에서 서버 가격 검증이 필요하다.

### 제외

- 주문 상태. 이번 범위에서는 상태 필드를 두지 않는다. PRD 4.11의 진행 중/지난 주문 구분과 4.12의 상태 표시는 다음 범위로 미루고, 주문내역은 최신순 단일 목록으로 제공한다.
- 주문 취소, 주문 수정 API.
- 서버 장바구니. 장바구니는 클라이언트 상태다.
- 옵션(Modifier), 할인, 세금, 결제 수단 기록.

주문번호 분리(`numberPrefix`, `number`), 항목 스냅샷(`OrderItem`), 요청사항(`request`)은 이전 서비스의 GraphQL 스키마(`Order`, `OrderItem`)를 참고했다. 이전 스키마의 `diningState`는 사용하지 않는다.

## 데이터 스키마 (PostgreSQL)

```sql
CREATE TABLE "order" (
  id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id integer NOT NULL,
  store_id integer NOT NULL,
  store_name varchar(100) NOT NULL,
  cart_id varchar(64) NOT NULL,
  order_date date NOT NULL,
  prefix_order_number varchar(10) NOT NULL,
  order_number integer NOT NULL,
  amount integer NOT NULL,
  request varchar(100),
  paid_at timestamptz NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT order_user_id_cart_id_unique UNIQUE (user_id, cart_id),
  CONSTRAINT order_store_id_order_date_number_unique
    UNIQUE (store_id, order_date, order_number)
);

CREATE TABLE order_item (
  id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  order_id integer NOT NULL,
  product_id integer NOT NULL,
  sku_id integer NOT NULL,
  product_name varchar(100) NOT NULL,
  sku_name varchar(100) NOT NULL,
  price integer NOT NULL,
  quantity integer NOT NULL
);

CREATE TABLE order_number_counter (
  store_id integer NOT NULL,
  order_date date NOT NULL,
  last_number integer NOT NULL,
  PRIMARY KEY (store_id, order_date)
);

CREATE INDEX order_user_id_created_at_idx ON "order" (user_id, created_at DESC, id DESC);
CREATE INDEX order_item_order_id_idx ON order_item (order_id);
-- 수동으로 주문을 수정할 때는 updated_at = now()를 함께 지정한다.
```

- `order`는 PostgreSQL 예약어다. 기존 `"user"`처럼 단수형 이름을 유지하고, raw SQL에서는 항상 `"order"`로 쓴다.
- `order_item.price`는 단가다. 항목 순서는 `order_item.id` 오름차순, 즉 입력 순서다.
- `store_name`은 주문 시점의 매장 이름 스냅샷이다. 매장 이름이 바뀌거나 매장이 비활성화되어도 주문내역은 주문 당시 이름을 보여준다.
- `order_date`는 서버가 `(now() AT TIME ZONE 'Asia/Seoul')::date`로 계산한다. 주문번호는 이 날짜 기준으로 매장마다 1부터 다시 시작한다.
- `paid_at`은 클라이언트가 보낸 결제 승인 시각이다. 결제 후 재시도로 `createOrder`가 늦게 도착해도 실제 결제 시각을 기록하기 위해 서버 시각을 쓰지 않는다.
- `order_number_counter`는 매장당 하루 한 행이다. 정리 작업은 두지 않는다.
- 기존 방침대로 외래 키는 추가하지 않는다. DDL과 샘플 데이터는 사용자가 직접 실행하며 저장소에 SQL·seed 파일을 추가하지 않는다. 샘플 데이터 SQL은 구현 결과에 제공한다.

## GraphQL 계약

모든 API는 기존 전역 `AuthGuard`를 통과해야 한다. 사용자 ID는 인자로 받지 않고 access token에서 얻은 `req.userId`만 사용한다.

```graphql
type Mutation {
  createOrder(input: CreateOrderInput!): Order!
}

type Query {
  orders(size: Int = 20, cursor: String): OrderPage!
  order(id: ID!): Order
}

input CreateOrderInput {
  cartId: String!
  storeId: ID!
  amount: Int!
  request: String
  paidAt: DateTime!
  items: [OrderItemInput!]!
}

input OrderItemInput {
  productId: ID!
  skuId: ID!
  productName: String!
  skuName: String!
  price: Int!
  quantity: Int!
}

type Order {
  id: ID!
  storeId: ID!
  storeName: String!
  prefixOrderNumber: String!
  orderNumber: Int!
  amount: Int!
  request: String
  items: [OrderItem!]!
  paidAt: DateTime!
  createdAt: DateTime!
}

type OrderItem {
  id: ID!
  productId: ID!
  skuId: ID!
  productName: String!
  skuName: String!
  price: Int!
  quantity: Int!
}

type OrderPage {
  items: [Order!]!
  nextCursor: String
}
```

- 화면의 주문번호는 `prefixOrderNumber + orderNumber`(예: `A12`)로 표시한다. `order.id`는 화면에 표시하지 않고 상세 조회 키로만 쓴다.
- `storeId`는 주문 상세에서 매장 상세로 이동할 때 쓴다.
- `updatedAt`, `cartId`, `orderDate`는 노출하지 않는다.

### 입력 검증

규칙을 벗어나면 `BAD_USER_INPUT`을 반환한다.

| 필드 | 규칙 |
|---|---|
| `cartId` | 1–64자 |
| `storeId`, `productId`, `skuId`, `id` | 기존 `validateId` (양의 32비트 정수 문자열) |
| `storeId` | `store` 테이블에 행이 있어야 한다. 활성·영업 여부는 보지 않는다. 없으면 `Store not found` |
| `items` | 1–50개. 같은 `skuId`가 여러 번 와도 각각 별도 항목으로 저장한다 |
| `productName`, `skuName` | 1–100자 |
| `price`, `amount` | 0 이상 정수 |
| `quantity` | 1–99 |
| `request` | 100자 이하. 빈 문자열이면 `null`로 저장한다 |
| `paidAt` | GraphQL `DateTime` 형식. 값 범위는 검사하지 않는다 |
| `size` | 1–50 (기존 `validateFirst`를 `validateSize`로 이름 변경) |

## 주문 생성 규칙

### `cartId`로 중복 생성 방지

결제 후 `createOrder` 응답이 유실되어 앱이 재시도하면 같은 결제로 주문이 두 번 생길 수 있다. 이를 `UNIQUE (user_id, cart_id)`로 막는다.

- `cartId`는 **결제된 장바구니 1회**의 식별자다. 주문이 성공하면 클라이언트는 장바구니를 비우고 새 `cartId`를 발급해야 한다. 같은 `cartId`를 다음 주문에 재사용하면 새 주문 대신 이전 주문이 반환된다.
- 같은 사용자가 같은 `cartId`로 다시 요청하면 오류 없이 기존 주문을 반환한다.
- `user_id`를 함께 묶으므로 다른 사용자의 `cartId`와 겹쳐도 서로 영향이 없고, 다른 사용자의 주문이 반환되지도 않는다.

### 주문번호 부여

매장·주문일별 순번을 카운터 테이블 upsert로 부여한다.

```sql
INSERT INTO order_number_counter (store_id, order_date, last_number)
VALUES (?, (now() AT TIME ZONE 'Asia/Seoul')::date, 1)
ON CONFLICT (store_id, order_date)
DO UPDATE SET last_number = order_number_counter.last_number + 1
RETURNING last_number, order_date;
```

- 행이 없으면 1로 만들고, 있으면 1 증가시킨 값을 반환한다.
- 주문일은 DB가 한 번만 계산하고, 반환된 `order_date`를 주문 INSERT에 그대로 쓴다. 카운터와 주문의 날짜가 어긋나지 않는다.
- 동시 주문은 upsert가 잡는 행 락으로 직렬화된다. 뒤 트랜잭션은 앞 트랜잭션의 커밋을 기다린 뒤 최신 값에 1을 더한다. 그날 첫 주문이 동시에 들어오면 기본 키가 직렬화한다. `SELECT MAX(...) + 1` 방식은 두 트랜잭션이 같은 값을 읽으므로 쓰지 않는다.
- 락은 `(매장, 주문일)` 한 행에만 걸리므로 다른 매장의 주문은 서로 기다리지 않는다.
- 카운터 증가와 주문 저장을 한 트랜잭션에서 실행한다. 주문 저장이 실패하면 증가도 롤백되므로 번호에 빈칸이 생기지 않는다.
- `prefixOrderNumber`는 서비스 상수 `'A'`로 저장한다.

### 처리 순서

```text
1. ID 형식 검증
2. SELECT id FROM "order" WHERE user_id = ? AND cart_id = ?
   └ 있으면 findOrder 결과를 반환한다
3. SELECT name FROM store WHERE id = ?
   └ 없으면 BAD_USER_INPUT 'Store not found'
4. em.transactional:
   a. 카운터 upsert → order_number
   b. INSERT "order" ... RETURNING id
   c. INSERT order_item 여러 행을 한 문장으로
5. 4가 order_user_id_cart_id_unique 위반(23505)으로 실패하면
   같은 cartId 요청이 동시에 들어온 것이다. 2번 조회를 다시 해 기존 주문을 반환한다.
   그 밖의 오류는 그대로 던진다.
6. findOrder 결과를 반환한다
```

- 매장 조회는 트랜잭션 밖에서 한다. 같은 매장 주문이 직렬화되는 구간은 4a–4c뿐이다.
- 응답은 `order(id)`와 같은 조회 경로로 만든다.

## 조회 규칙

- `orders(size, cursor)`: 현재 사용자의 주문을 `created_at` 내림차순, `id` 내림차순으로 반환한다.
  - 주문 조회와 항목 조회(`WHERE order_id = ANY(?)`) 두 번으로 끝나므로 N+1이 없다.
  - 커서는 기존 `encodeCursor`/`decodeCursor`를 쓴다. `kind`는 `'orders'`, `scope`는 `String(userId)`, 키는 `created_at`과 `id`다. 다른 사용자의 커서는 `Invalid cursor`로 거절한다.
  - `size + 1`건을 조회해 다음 페이지 여부를 판단하는 기존 `slicePage`를 쓴다.
- `order(id)`: `WHERE id = ? AND user_id = ?`로 조회한다. 없거나 다른 사용자의 주문이면 `null`을 반환한다. 존재 여부를 드러내지 않기 위해 권한 오류를 쓰지 않는다.

### 1단계: 리팩터 (동작 변경 없음)

| 현재 | 변경 |

| `src/stores/stores.util.ts`의 `CursorKind`, `encodeCursor`, `decodeCursor`, `slicePage`, `validateFirst` | `src/common/pagination.ts`로 이동. `validateFirst`는 `validateSize`로 이름 변경 |
| `stores`, `newStores`, `search.stores`, `search.menus`의 `first`, `after` 인자 | `size`, `cursor` |

- 응답 필드 `nextCursor`는 유지한다. 다음 요청의 `cursor`에 그대로 넣는 값이다.
- 인자 이름 변경은 기존 API 계약을 바꾼다. 클라이언트가 이미 `first`, `after`를 쓰고 있다면 함께 수정한다.

### 2단계: 기능

```text
src/common/pagination.ts   CursorKind에 'orders' 추가, 날짜 키 검증을 'new'와 'orders'에 적용
src/orders/
  orders.types.ts          Order, OrderItem, OrderPage, CreateOrderInput, OrderItemInput
  orders.service.ts        createOrder, findOrders, findOrder
  orders.resolver.ts
  orders.module.ts
src/app.module.ts          OrdersModule 등록
```

- 모든 읽기와 쓰기를 `em.execute` raw SQL로 처리하므로 엔티티와 `forFeature`는 만들지 않는다.
- 입력 형식 규칙은 기존 `SignUpInput`처럼 class-validator 데코레이터로 선언한다. 중첩 항목은 `@ValidateNested`와 `@Type`을 쓴다. ID 형식은 서비스에서 `validateId`로 검증한다.
- resolver는 `@Context('req')`의 `userId`를 서비스에 넘긴다.

## 검증

단위 테스트는 `em`을 mock하며 DB 없이 실행할 수 있어야 한다. 테스트 이름은 `~하면 ~한다` 형식으로 쓴다.

- 리팩터 후 기존 테스트가 모두 통과하고, `schema.gql`의 기존 페이지 인자가 `size`, `cursor`로 바뀐다.
- `orders` 커서 인코딩·디코딩, 다른 `scope` 커서 거절.
- 기존 `cartId`면 INSERT 없이 기존 주문 반환.
- 없는 매장의 `Store not found` 입력 오류.
- 정상 생성 시 카운터 upsert, 주문 INSERT, 항목 INSERT를 한 트랜잭션에서 실행하고 DB 매장명과 `'A'`를 저장.
- 빈 `request`의 `null` 저장.
- `cart_id` unique 위반 시 기존 주문 반환, 그 밖의 DB 오류 전파.
- 목록의 사용자 조건, 항목 묶음과 순서, 마지막 페이지의 `nextCursor` `null`.
- 다른 사용자 주문 상세의 `null` 반환, 잘못된 ID의 입력 오류.
- resolver의 `req.userId` 전달.
- 입력 규칙 위반의 `BAD_USER_INPUT` (`cartId` 길이, `items` 0개·51개, `quantity` 0·100, 음수 `price`·`amount`, 이름·`request` 길이).
- `schema.gql`에 `createOrder`, `orders(size, cursor)`, `order(id)` 노출.

통합 테스트(`test/orders/orders.integration-spec.ts`)는 `TEST_DATABASE_URL`과 DDL이 적용된 테스트 DB에서 실행한다. 테스트용 매장과 주문 행은 직접 만들고 끝나면 지운다.

- 같은 매장에 `createOrder` 10건을 동시에 보내면 주문번호가 1–10으로 중복 없이 부여된다. 소요 시간을 출력해 직렬화 비용을 측정한다.
- 같은 `cartId`로 2건을 동시에 보내면 주문이 하나만 생기고 두 응답의 `id`가 같다.
