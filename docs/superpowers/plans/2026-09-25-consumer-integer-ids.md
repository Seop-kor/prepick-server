# Consumer discovery integer IDs implementation plan

> 이 계획의 인증 UUID 유지 문구는 당시 구현 범위의 기록이다. 현재 인증 ID도 [정수 ID 전환 설계](../specs/2026-09-25-auth-integer-ids-design.md)에 따라 변경한다.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Change `store`, `product`, `sku`, and `promotion` identifiers from UUID to PostgreSQL generated `integer` while preserving the user's existing rows and product relationships.

**Architecture:** Keep GraphQL `ID` fields and query names; PostgreSQL and MikroORM use 32-bit integers. The cursor stores a numeric final ID. Provide a manually executed, transactional database migration that keeps old UUID columns for rollback. Auth identifiers stay UUID.

**Tech Stack:** NestJS GraphQL, MikroORM 7, PostgreSQL, Jest.

**Spec:** `docs/superpowers/specs/2026-09-25-consumer-store-discovery-design.md`

## Global Constraints

- Do not change persistent user tables or data. The user runs the documented migration manually; temporary-table rollback verification is allowed.
- Preserve every existing store, product, SKU, and promotion row and both product relationships.
- The four GraphQL `ID` fields continue to be GraphQL `ID`; their values change to decimal integer strings.
- Use PostgreSQL `integer GENERATED BY DEFAULT AS IDENTITY`, with the sequence advanced above migrated IDs.
- Keep the omitted `REFERENCES` and `CHECK (price >= 0)` constraints omitted.
- Tests use Korean names in the `~ 하면 ~ 한다` form.

## Review Focus

- A malformed, zero, negative, or out-of-range ID returns an input error.
- A UUID cursor cannot be reused after the identifier change.
- An integer cursor keeps the last row's numeric ID and still separates equal sort keys.
- Raw query rows hydrate numeric IDs and nested store IDs correctly.
- Migrated product and SKU relationships remain intact, and the next insert gets a new ID.
